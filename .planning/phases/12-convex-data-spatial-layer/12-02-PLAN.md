<objective>
Execute P12-04/P12-05: build the Convex spatial layer that replaces the PostGIS spatial queries the app uses (ST_DWithin / ST_Distance / ST_Extent / ST_MakePoint), and prove it returns parity results vs the live PostGIS output. Per the research decision (RESEARCH §1), this uses a clean split: the official @convex-dev/geospatial component (Beta) nearest()/query() for POINT datasets (chargers, carriers, parking, pois, ports) where nearest-within-radius + an in-index class8 filter is the exact fit, and the Phase-7 hand-rolled bbox+haversine pattern for LINE/segment data (highwaySegments, corridors, nhfnSegments). The non-negotiable design constraint is that BOTH sit behind ONE internal module (convex/lib/spatial.ts) so downstream queries (12-04 charger gap, 12-08 report query) never import the component directly and the impl can swap to the pure-haversine fallback if the Beta component bites — the fallback (convex/lib/haversine.ts) is fully implemented here, covers points too, and is proven against the same parity fixtures, so the component is an optimization, not a dependency. The parity gate (P12-05) captures the live docker PostGIS chargers-near output for the POLB and Cajon corridor points as fixtures and asserts the Convex spatial layer returns the identical station set within the query radius, distances within 0.1 mi. This plan is Wave 1 (depends on 12-01's tables) and blocks the charger-gap parity re-run in 12-04 and the report query in 12-08. It does NOT ingest chargers (12-04 does) — it proves the spatial math + harness against captured ground truth.
</objective>
