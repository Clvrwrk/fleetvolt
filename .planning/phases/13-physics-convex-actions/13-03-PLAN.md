# Plan 13-03: Parity Validation — Python vs Convex TS

<objective>
Prove the Convex TS physics engine produces numerically identical results to the Python engine within the locked tolerance (±0.5% energy/SoC, exact on feasibility tier + charging-stop count). Capture Python baselines from the live simulator, then run the Convex simulate action on the same inputs and compare. Two validation cases: POLB drayage (corridor with grade) and flat highway (synthetic OEM reference). This is the highest-risk gate of the entire v3.0 migration — a parity failure here means the rewrite is not trustworthy.
</objective>

<execution_context>
Monorepo root: /Volumes/M4 Application SSD/Projects/FleetVolt. Docker stack: docker-compose.yml with simulator (FastAPI :8000), postgres (PostGIS :5432), redis (:6379). The Python simulator exposes POST http://localhost:8000/v1/simulate accepting SimulateRequest JSON (route, truck, conditions, overrides, options). The test vector (from inputs_hash.py TEST_VECTOR_SCENARIO): corridor_key=polb_cajon_pass, truck slug=ecascadia_438, weather=ideal, payload_lbs=34000, port_drayage_enabled=false, include_charging=true. The flat_highway_oem case: origin {34,-118}, dest {34,-117}, 230mi flat, 65mph, 45000 lbs, ecascadia_438. Convex dev deployment: sensible-oriole-832 with truckConfigs + elevationProfiles + corridors seeded (Phase 12). The Convex simulate action (13-02) runs as a Convex action. Parity tolerance: ±0.5% on total_kwh + per-segment soc_pct; EXACT match on feasibility.verdict + feasibility.tier + charging_stops.length.
</execution_context>
